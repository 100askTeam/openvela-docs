基于VirtIO的跨核通信

VirtIO的概念​

概念与作用​

VirtIO 是虚拟化领域中一种半虚拟化（Paravirtualization）的 I/O 技术标准。它的核心目标是：在虚拟化环境下，为虚拟机（Guest）提供一种高效、标准化的 I/O（输入/输出）抽象层，从而大幅提升网络、磁盘等设备的性能，同时避免为每个虚拟设备编写复杂的全硬件模拟代码。

在没有 VirtIO 这类技术时，传统的虚拟化 I/O 主要有两种方式：

① 全虚拟化（Full Virtualization） Hypervisor 完全模拟真实的物理硬件（如 Intel e1000 网卡、IDE 磁盘）。这种方式兼容性最好，Guest 无需修改就能运行，但性能很差——因为每次 I/O 操作都要经过复杂的硬件指令模拟、多次上下文切换，并且数据需要多次拷贝。

② 设备直通（Device Pass-through） 如 PCI 直通或 SR-IOV，将物理设备直接分配给虚拟机。性能接近物理机，但成本高、灵活性差（一台设备只能分配给一个虚拟机），且不支持热迁移等高级功能。

VirtIO 试图在“兼容性”和“性能”之间找到一个平衡点——它定义了一套虚拟设备的标准接口，让 Guest 和 Hypervisor 之间能够以高吞吐、低延迟的方式通信，同时保持较好的通用性。

VirtIO 采用 前端（Front-end）/后端（Back-end） 架构：

.  前端驱动（Front-end Driver）

运行在虚拟机内部（Guest OS）。它是一个标准的设备驱动，比如 VirtIO-net、VirtIO-blk，但不会去模拟具体的硬件寄存器，而是通过一种称为 virtqueue 的共享内存环形队列与后端通信。

② 后端设备（Back-end Device）

运行在 Hypervisor（宿主机）中，负责真正处理 I/O 请求。例如 QEMU 中的 VirtIO-net-pci 设备或 vhost 内核模块。后端将请求翻译为对宿主机物理硬件或文件的 I/O 操作。

③ virtqueue（虚拟队列）

前端和后端之间通过共享内存进行数据交换，避免陷入（trap）和模拟指令的开销。virtqueue 是一种高效的环形缓冲区（Ring Buffer），用于存放 I/O 请求和响应，配合 零拷贝（Zero Copy） 技术，进一步减少数据复制。

④ VirtIO 规范（Specification）

定义了设备类型（块设备、网络设备、控制台等）、配置空间、virtqueue 操作方式等。这套规范由 OASIS 标准化，保证了不同 Hypervisor（如 QEMU/KVM、Cloud Hypervisor）和不同 Guest OS（Linux、Windows）之间的互操作性

使用VirtIO可以在Guest和Host之间通信，双方通信的本质是使用基于共享内存的环形缓冲区。而一个芯片内部两个核之间也有共享内存，那么VirtIO也就可以用于跨核通信。VirtIO用作虚拟化时需要有guest-host。现在使用VirtIO来进行跨核通信，那么仍然要提供2个角色：guest-host， 只不过guest、host地位是平等的，guest不是运行在host上面。如下图所示：

使用场景​

在跨芯片传输时RPMSG中通常使用UART、SPI作为传输层，但是在芯片内跨核传输时更多使用“基于共享内存的VirtIO”作为传输层，可以提高数据传输速率。

VirtIO 提出了以下两种核心机制：

① 特性扩展机制。

a. 提供适用于所有驱动的 feature 扩展机制，便于扩展 VirtIO driver 的功能。

b. 支持 feature 的协商，确保向前和向后兼容性。

② 基于共享内存的数据传输机制（vring/virtqueue）。

适用于所有驱动，设计简单，支持零拷贝和无锁操作，更有通知抑制和批量提交等高级特性。

VirtIO的本质（环形缓冲区）与层次​

环形缓冲区​

使用共享内存进行跨核通信时，特别适合使用环形缓冲区：

① 一方写buffer

② 另一方读buffer。

环形缓冲区实际上还是一维数组，假设有N个数组项，从第0个数组项开始遍历，访问完第N-1个数组项后，再从0开始——这就是“环形”的含义，如下图所示：

环形缓冲区的工作原理如下图所示：

使用过程分析如下：

① 环形缓冲区有读位置、写位置：r、w，它们表示“下一个要读的位置”、“下一个要写的位置”，初始值都是0

② 写数据时：把数据写入buffer[w]，然后调整w指向下一个位置（当w越界后要从0开始）

③ 读数据时：从buffer[r]读出数据，然后调整r指向下一个位置（当r越界后要从0开始）

④ 判断buffer为空：r等于w时表示空

⑤ 判断buffer为满：“下一个写位置”等于当前读位置

改进的缓冲区​

在跨核系统使用环形缓冲区时，假设下图的buf[0]~buf[3]比较大，不仅仅是用来存放一个整数，而是用来存放一帧数据：

那么就会涉及2次拷贝过程：

① core0产生数据时（比如读取硬件得到数据），要拷贝进buf[0]

② core1消费数据时，要从buf[0]拷贝出来

可以如下图改造以实现“零拷贝”：

① core0产生数据时，直接把存有数据的buffer地址（比如addr1、addr2）写入环形缓冲区里

② core1消费数据时，从buf[0]、buf[1]得到地址，使用地址去访问数据。

virtio的本质​

virtio的本质，也是使用环形缓冲区在两个核之间传输数据：

① 两个核之间使用1个或多个Virtqueue来传输数据

② 1个Virtqueue里面有2个环形缓冲区：avail ring、used ring

③ 这2个环形缓冲区里存放有整数：表示“Descriptor Table”的哪个数组项

④ “Descriptor Table”被用来描述缓冲区，结构体如下：

/**

* @brief VirtIO 环描述符。

*

* 描述符表引用驱动程序正在为设备使用的缓冲区。addr 是一个物理地址，

* 缓冲区可以通过 \ref next 字段进行链式连接。

* 每个描述符描述一个对设备只读（“device-readable”，即设备可读/驱动可写）

* 或对设备只写（“device-writable”，即设备可写/驱动可读）的缓冲区，

* 但一个描述符链中可以同时包含设备可读和设备可写的缓冲区。

*/

struct vring_desc {

/** 地址（客户机物理地址 / guest-physical） */

uint64_t addr;

/** 长度 */

uint32_t len;

/** 与描述符相关的标志位 */

uint16_t flags;

/** 我们也通过此字段链接未使用的描述符 */

uint16_t next;

};

使用场景如下：

① “VirtIO Driver”分配好buffer，填入“Descriptor Table”

② “VirtIO Driver”会在这2种情况下写avail ring：
a. 想发数据给“VirtIO Device”：在buffer里填充好数据后，要把它在“Descriptor Table”中的索引写入avail ring。

b. 想把buffer提供给“VirtIO Device”以便它写入数据：“VirtIO Driver”无需写buffer，也可以把它在“Descriptor Table”中的索引写入avail ring。

③ “VirtIO Device”读取avail ring获得buffer：可以读取里面的buffer获得数据，也可以把数据写入buffer，最后需要包buffer在“Descriptor Table”中的索引写入used ring。

④ “VirtIO Driver”读取used ring：获得“VirtIO Device”返回的数据。

virtio的层次​

跟rpmsg层次类似，VirtIO也可以分为三层，下面结合“环形缓冲区的本质”来解读：

① VirtIO 服务层：服务层通过调用 VirtIO 提供的统一接口，完成设备的初始化和数据交互，实现各类功能，比如VirtIO-RNG、VirtIO-blk等。

简单地说，就是两端的服务层使用“环形缓冲区”交换数据，完成各类功能。

② VirtIO 框架层：VirtIO 层为驱动提供统一的接口，支持 Driver 和 Device 的注册、卸载以及匹配机制。

简单地说，框架层主要提供“环形缓冲区”的接口函数，提供各类注册函数给服务层、传输层使用。

③ VirtIO 传输层：传输层提供对不同传输方式的支持，包括 MMIO、RemoteProc 和 PCI 等。

简单地说，传输层主要实现“环形缓冲区”接口函数的底层代码。

理解VirtIO的关键点​

关键点在于：

① 双方如何发现同一个共享内存，并且都能访问到

② 双方如何约定：在这个共享内存上实现什么功能（比如VirtIO RNG等）

③ 一方分配环形缓冲区（Vring），另一方为何能看到并且直接使用

④ 如何创建virtqueue

⑤ 如何使用VirtQueue来传输数据

openvela的总线设备驱动模型​

要理解VirtIO的代码，要先学习openvela里驱动程序的编写模式：总线设备驱动模型。

常规驱动的缺点​

以下图的LED电路为例：

按照常规编写驱动程序的方法，要构造一个file_operations结构体，示例如下：

static const struct file_operations g_led_fops =

{

led_open, /* open */

led_close, /* close */

led_read, /* read */

led_write, /* write */

NULL, /* seek */

NULL, /* ioctl */

NULL /* poll */

};

在led_open函数里初始化引脚PIN1为输出功能，在led_write函数里根据传入的参数设置PIN1输出高电平或低电平。

这种方法有2个缺点：

① 要把引脚从PIN1改为PIN2时，你需要去理解驱动程序的操作细节，然后才能修改

② 要支持PIN1、PIN2两个LED时，需要把PIN1驱动复制一份并改为PIN2

总线设备驱动模型​

要去操作LED时，需要确定2个因素：使用哪个引脚（资源），怎么操作引脚（操作方法）。可以把“资源”、“操作方法”区分开来，比如把“资源”写入led_device.c，把操作方法写入led_driver.c。这样的好处是：要修改引脚时，只需要查看修改led_device.c，无需查看复杂的led_driver.c。并且，如果程序设计得当，可以让led_driver.c支持多个“资源”（比如支持PIN1、PIN2、……）。

这样的程序结构如下：

使用步骤如下图所示：

① 有一个全局结构体g_led_bus，称之为“总线”，它里面有2个链表：driver、deivces

② led_device1.c里构造了一个led_deivce结构体，称之为“设备”，里面含有“ID”、引脚“PIN1”、使用方式“ACTIVE_LOW”。使用“led_register_device(&led1)”把这个“设备”注册进“g_led_bus.device”链表。

③ 在led_register_device函数里，它还会把led1跟“g_led_bus.driver”中的每一个“驱动”进行比较，如果两者ID相同，就调用“驱动”的probe函数。

④ t113_led_driver.c里构造了一个led_driver结构体，称之为“驱动”，里面含有“ID”、枚举函数“probe”。使用“led_register_device(&t113_led_drv)”把这个“驱动”注册进“g_led_bus.driver”链表。

⑤ 在led_register_driver函数里，它还会把t113_led_drv跟“g_led_bus.device”中的每一个“设备”进行比较，如果两者ID相同，就调用“驱动”的probe函数。

如此一来，无论是先注册“设备”还是先注册“驱动”，两者都会一一比较。“驱动”的probe函数里，可以去注册“file_operations”实现常规的驱动程序注册。

注意：总线设备驱动模型，只是提供了一种“分离”的机制——把硬件资源、操作方法分离开来。至于probe函数里做什么，完全由你决定。
