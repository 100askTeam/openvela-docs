配置与编译总体流程​

openvela里各个子目录可以看到Makefile、Make.defs、Make.dep，这3类文件的作用为：

  • Makefile：里面定义了编译的规则

  • Make.defs：用于管理参与编译的源文件列表

  • Make.dep：编译时生成的依赖规则，不用看

编译过程​

理解nuttx编译过程的关键字为“递归”。我们把nuttx的Makefile分为多个级别，如下：

  • 在“顶层目录”nuttx下执行“make”

  • 会分别进入第2层目录执行“make”：比如进入apps目录、sched目录分别执行“make”

  • 在apps目录下执行“make”，又会进入第3层目录执行make：比如进入“apps/builtin”、“apps/examples/hello”目录下执行“make”

执行“m”命令编译时，会执行“make -C nuttx”，就是进入nuttx目录执行它里面Makefile的第1个目标“all”，这个目标的依赖关系为:

编译Nuttx时，本质是进入nuttx目录执行“make all”，nuttx由staging目录下的各个“.a”文件组成：

$ ls staging/

libapps.a libarch.a libbinfmt.a libboards.a libc.a libcrypto.a

libdrivers.a libfs.a libmm.a libsched.a libxx.a

所以要先生成这些“.a”文件。

以libapps.a为例。在apps目录的源码里，它需要包含“include/nuttx/config.h”文件，使用里面的宏进行作为源码的条件编译开关。所以要生成libapps.a，要先生成config.h，这被称为“context”（上下文）。

从顶层nuttx/Makefile开始，会进入apps目录、sched目录等目录，逐个编译出对应的“.a”文件，然后再把它们连接起来得到nuttx。

在编译apps等目录时，又会先处理“context”等目标，然后才开始才编译代码。这些操作，都依赖于各个目录下的Makefile，比如apps/Makefile、sched/Makefile。

这样，控制流程就从顶层nuttx/Makefile进入了下一级的Makefile。

进入下一级目录构建context​

在顶层目录nuttx下执行make去编译libapps.a、libsched.a之前，都会先构建“context”。它会进入apps、sched目录使用它们的Makefile构建context：

make -C apps context

以“apps/Makefile”为例，它的context规则如下：

context: | staging

$(Q) $(MAKE) context_all

$(Q) $(MAKE) register_all

$(Q) $(MAKE) context_wasm

上述规则会再次进入“CONFIGURED_APPS”指定的下一级目录执行“make context”、“make register”等。

注意：apps目录下各个子目录的Makedefs里，定义了“CONFIGURED_APPS”变量，它的值大概是这样：

CONFIGURED_APPS = /.../apps/builtin /.../apps/examples/hello ...

所以，会使用类似下面命令进入下一级：

make -C /.../apps/builtin register

make -C /.../apps/examples/hello register

进入下一级目录构建.o​

在顶层目录nuttx下执行make去编译libapps.a、libsched.a时，执行的是类似下面的命令（简化了）：

make -C apps all

make -C sched all

就是：顶层Makefile进入下一级的目录，使用它们的Makefile去构建all目标。

当构建apps/Makefile里的all目标时，它确定了“CONFIGURED_APPS”后，又分别进入这个变量表示的下一级目录，使用它们的Makefile构建各自的all目标，比如：

make -C apps/builtin all

make -C apps/example/hello all
