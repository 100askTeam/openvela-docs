### SPI驱动子系统框架

从硬件的角度看，主控芯片通过SPI控制器去访问SPI设备：

- SPI控制器负责SPI传输，它并不了解传输的数据含义：它只提供传输能力

- 我们需要阅读SPI设备手册，才能知道所收发的数据的含义

从应用程序角度看：

- SPI控制器驱动程序提供了传输能力

- APP可以直接通过SPI控制器驱动程序来读写SPI设备，这时编写APP的人需要阅读芯片手册

- APP可以通过SPI设备驱动程序来读写SPI设备，编写设备驱动程序的人需要阅读芯片手册，他编写的驱动程序可以让APP开发人员更轻松地使用SPI设备

从驱动程序的角度看，SPI控制器驱动程序分为上半部、下半部，上半部把接口固定下来并实现通用的代码；下半部是硬件相关的代码。SPI设备驱动程序也可以分为上半部、下半部。下图的SPI设备以spi lcd为例。

### SPI控制器驱动上半部

#### 下半部核心结构体

分析：nuttx/drivers/spi/spi_driver.c

我们从上往下分析更容易：从APP角度看问题可以不执着于底层硬件的操作细节。但是对于SPI控制器驱动的下半部，需要先有个大概认识，这有助于看懂上半部的代码。

从SPI硬件的连线图可知，一个SPI控制器上面可以连接多个SPI设备。那么在进行SPI传输时就必须明确这几点：

- 访问哪个设备？每个SPI设备都有自己独一的片选引脚，在访问这个SPI设备前，要先“选中”它

- 传输频率等参数设置

- SPI传输时，必定是发送多少个字节就能接收到多少个字节

上述信息使用这2个结构体来描述：

- spi_sequence_s：被用来描述SPI“传输序列”，里面有SPI设备编号、频率、SPI模式等信息，含有一个“spi_trans_s”指针

- spi_trans_s：它表示一个“SPI传输”，里面含有“txbuffer”、“rxbuffer”、数据长度

### Framebuffer的基本概念

APP参考代码：apps/examples/fb/fb_main.c

驱动参考代码：nuttx/drivers/video/goldfish_fb.c

#### 软件工程师眼里的LCD

LCD就是由多行、多列的像素组成的点阵，如下：

![](/img/openvela/image88.png)

只要能控制每个像素的颜色，就可以在LCD上绘制文字、图片；不断改变文字、图片就能显示动态效果。

最简单的办法就是：有一块内存被用来保存每一个像素的颜色，这个内存就Framebuffer。Frame是帧的意思，buffer是缓冲的意思，这意味着Framebuffer就是一块内存，里面保存着一帧图像。Framebuffer中保存着一帧图像的每一个像素颜色值，假设LCD的分辨率是320x480，每一个像素的颜色用32位来表示，那么Framebuffer的大小就是：320x480x16/8=307200字节。如下图所示：

![](/img/openvela/image89.png)

Framebuffer有可能在LCD里面，也可能在LCD之外，下图所示的LCD上含有Framebuffer，只要主控通过SPI把数据写入Framebuffer即可显示：

![](/img/openvela/image90.png)

下图所示的LCD上没有Framebuffer，Framebuffer在外接的内存上。需要一个“LCD控制器”周而复始地读取Framebuffer的数据再发给LCD：

![](/img/openvela/image91.png)

对于第1种“含有Framebuffer”的LCD，软件开发人员需要“构造数据、然后通过SPI发给LCD”。对于第2种“没有Framebuffer”的LCD，软件开发人员只需要“把数据写入Framebuffer”即可。

为了解决这2种操作方法的差异，在第1种LCD上再次引入一个Framebuffer，如下图所示：

![](/img/openvela/image92.png)

在APP人员的眼里，他只需要把像素数据写入“APP看到的Framebuffer”，驱动程序会周而复始地把这些数据通过SPI发给LCD，存入LCD自己的Framebuffer。

#### Framebuffer基本参数

使用Framebuffer来描述一帧像素，关键参数有：分辨率、像素颜色格式。

所谓像素颜色格式，就是怎么表示每个像素的颜色？LCD像素的颜色是用RGB三原色(红、绿、蓝)来表示的，在不同的颜色格式中，用不同的位来分别表示R、G、B，如下图所示：

![](/img/openvela/image93.png)

RGB888的意思是红绿蓝都是使用8bit数据来表示，一般只设置其中的低24位，高8位表示透明度，一般的LCD都不支持。一个像素占据32bit数据，称为32BPP。

对于24BPP，硬件上为了方便处理，在Framebuffer中也是用32位来表示，效果跟32BPP是一样的。

对于16BPP，常用的是RGB565；很少的场合会用到RGB555，

本实验的TFT LCD每个像素使用16位数据来表示它的颜色：

![](/img/openvela/image94.png)

LCD的分辨率是320\*480，那么需要320\*480\*16bit/8=307200字节的Framebuffer来保存所有像素的颜色。在Framebuffer里，依次保存着各个像素的颜色，如下图所示：

![](/img/openvela/image95.png)

#### SPI LCD操作方法

注意：本实验的LCD通过SPI接口把Framebuffer的数据发送给LCD时，它传输的第1个字节是“高字节数据”，第2个字节是“低字节数据”。为了提高SPI传输效率，在写Framebuffer里，把每个像素的2个字节颜色数据对调一下，如下图所示：

![](/img/openvela/image96.png)

怎么把这些颜色的数据，发给LCD？有两种方法：先在Framebuffer里绘制好每个像素，然后一次性地把整个Framebuffer的数据全部通过SPI接口发给LCD。这种方法有缺点：即使只修改几个像素的颜色，也要发送整个Framebuffer的数据。

第2种方法是：先设定一个区域，然后只发送这个区域的数据。比如只想修改如下图所示区域的6个像素：

![](/img/openvela/image97.png)

那么可以通过SPI接口发出设置命令，告诉LCD要修改的区域起始坐标为（3, 1），宽度为2，高度为3。然后再发送这6个像素总共12字节的颜色数据即可。

怎么设置指定位置的像素？假设需要设置LCD中坐标(x,y)处像素的颜色，首要要找到这个像素对应的内存，然后根据它的BPP值设置颜色。假设fb_base是Framebuffer的起始地址，如下图示：

#### 现代LCD控制器的Plane概念

（1）Plane的概念

在 LCD 显示系统中，Plane（平面） 是一个与显示缓冲区和图像合成相关的核心概念，尤其在嵌入式系统（如 NuttX 等）的 Framebuffer 驱动中频繁出现。它本质上是独立的图像数据缓冲区，用于存储一部分图像信息，最终通过硬件合成（通常由 LCD 控制器完成）显示在屏幕上。

现代 LCD 控制器通常支持多个 Plane（如 Plane0、Plane1、Plane2 等），每个 Plane 可独立存储不同的图像数据（如背景层、前景层、UI 控件层等）。控制器会按照预设的叠加规则（如透明度、优先级）将多个 Plane 的图像实时合成，最终输出到 LCD 面板。

例如：

- Plane0：存储静态背景图像（如桌面壁纸）

- Plane1：存储动态 UI 元素（如按钮、文本）

- Plane2：存储视频流数据（如摄像头画面）

多Plane可以降低系统开销：若没有多 Plane 支持，更新局部图像（如移动一个按钮）需重绘整个屏幕，导致大量显存读写和 CPU 占用。而多 Plane 机制下，只需更新对应 Plane 的局部数据，控制器会自动处理合成，显著提升效率。

部分高级 Plane 支持硬件特性，如：

- 像素格式转换（如 YUV 到 RGB）

- 缩放、旋转

- 透明度混合（Alpha blending）

- 色彩校正

（2）Plane 与 LCD 控制器、面板的关系

LCD 控制器：是 Plane 的 “管理者”，负责：

- 为每个 Plane 分配独立的显存区域

- 配置 Plane 的参数（分辨率、像素格式、起始地址等）

- 按照规则合成多个 Plane 的图像

- 将合成结果发送到 LCD 面板

- LCD 面板：是最终的 “显示载体”，不直接感知 Plane 的存在，只接收控制器输出的合成后的数据。

- Framebuffer 驱动：通过结构体（如 NuttX 中的struct fb_planeinfo_s）向上层暴露 Plane 的信息（如缓冲区地址、支持的像素格式），供应用层或图形库使用。

（3）单 Plane 与多 Plane 的典型场景

单 Plane：简单嵌入式设备（如小型 LCD1602、单色屏），只需一个缓冲区存储完整图像，适用于静态或低刷新率显示。

多 Plane：复杂场景（如智能终端、车载系统）：

车载显示：仪表盘（Plane0）+ 导航地图（Plane1）+ 警告图标（Plane2，高优先级）

智能家居：背景 UI（Plane0）+ 实时传感器数据（Plane1）+ 弹窗提示（Plane2）

#### Plane里的多buffer

对于一个Plane，可以给分配刚好保存一帧图像数据的Framebuffer。单 Framebuffer 的核心痛点是 “读写冲突”：当 CPU/GPU 正在向 Framebuffer 写入新图像数据（如刷新 UI、绘制动画）时，LCD 控制器可能同时从同一 Framebuffer 读取数据并输出到屏幕，导致屏幕上出现 “半新半旧” 的撕裂画面（尤其高刷新率场景）。

解决办法是给Plane分配可以保存多帧图像数据的Framebuffer。这样做的好处是：LCD控制器在读取buffer A的数据来显示时，APP可以在buffer B上构造下一副图像，当APP构造好后再让LCD控制器使用buffer B的数据。这使用LCD控制器使用的是“完整的数据”。

#### API函数

参考“apps/examples/fb/fb_main.c”，使用基于Framebuffer的LCD时，需要使用这些接口函数：

- 打开文件：open(fbdev, O_RDWR);

- 获得videoinfo：偏向于硬件参数，比如分辨率、像素格式、有几个plane，使用ioct FBIOGET_VIDEOINFO来获得

- 获得planeinfo：偏向于软件参数，比如Framebuffer地址、大小，双buffer等，使用ioctl FBIOGET_PLANEINFO

- 获得Framebuffer地址：调用mmap

- 对于多个Framebuffer，在某个Framebuffer里绘制好数据后，调用ioctl FBIOPAN_DISPLAY把这个Framebuffer显示出来

- 更新某个区域：这是可选的操作，使用ioctl FBIO_UPDATE

mmap函数稍微复杂，内存映射文件技术通过将文件直接映射到进程虚拟地址空间，实现零拷贝的高效I/O，并支持多进程通过MAP_SHARED标志共享内存。

函数原型如下：

\#include \&lt;sys/mman.h\&gt;

```
void \*mmap(

void \*start, // 映射区起始地址（通常设为NULL，由系统自动分配）\[\[3\]\]\[\[7\]\]

size_t length, // 映射区域的长度（以字节为单位）\[\[3\]\]\[\[9\]\]

int prot, // 内存保护标志（如PROT_READ、PROT_WRITE）

int flags, // 映射标志（如MAP_SHARED、MAP_PRIVATE）\[\[5\]\]\[\[6\]\]

int fd, // 文件描述符（匿名映射时设为-1）

```
off_t offset // 文件偏移量（需为页大小的倍数）

```
);

```
- 参数 ：

  - addr：建议的映射起始地址（通常设为 NULL，由内核自动分配）。

  - length：映射区域的长度。

  - prot：内存保护标志（如 PROT_READ、PROT_WRITE）。

  - flags：映射选项（如 MAP_SHARED、MAP_PRIVATE）。

  - fd：文件描述符（需通过 open 打开）。

  - offset：文件映射的起始偏移量（需为页大小的整数倍）。

- 返回值 ：

  - 成功返回映射区的起始地址，失败返回 MAP_FAILED（(void \*)-1）。

#### SPI设备驱动程序开发方法

在开发SPI设备驱动时需要知道：

- 它连接在哪个SPI控制器下面：要得到对应的“spi_dev_s”结构体，它提供了传输能力；还需要知道使用哪个片选引脚

- 还要阅读芯片手册：知道它的操作方法

- 最后，找到合适的“驱动程序上半部”并实现“下半部”：如果没有上半部，可以自己写一个单独的驱动程序

开发SPI LCD驱动程序时，有了“spi_dev_s”结构体，就有了数据传输能力，剩下操作就是：

- 根据硬件信息构造一个fb_videoinfo_s结构体：里面存放硬件参数

- 构造一个fb_planeinfo_s结构体：里面描述Framebuffer信息

- 构造一个fb_vtable_s结构体：里面含有LCD的操作函数，涉及SPI传输时使用“spi_dev_s”结构体

- 调用“fb_register_device”函数注册驱动
