#### unwind stack技术

“wind”的意思是“缠绕”（不取“风”的意思），比如这个函数调用“hello_main \&gt; A \&gt; B”会导致栈里存有它们的返回地址，这些“返回地址”一层一层存放在栈里——缠绕在栈里。

“unwind”就是“反缠绕”：从栈里反向把调用关系找出来。所以，“unwind”就是对栈的数据进行回溯（backtrace），得到调用关系。

在传统arm平台上unwind stack技术基本上有四种方式

- 基于DWARF CFI(\_Unwind_Backtrace)

- 基于arm eabi：对应openvela的“arm_backtrace_unwind.c”

- 基于frame pointer：对应openvela的“arm_backtrace_fp.c”

- 基于stack pointer：对应openvela的“arm_backtrace_sp.c”

前两种方式需要在编译阶段生成特殊的section（比如eh_frame section、text section）所以会增大整个code/data的size(overload + 5%-8%)，由于代码尺寸增加，在一般资源受限的嵌入式设备上就会遇到取舍问题，在cortex-m设备上8%的flash开销是非常宝贵的，所以大部分做cortex-m设备上都会考虑方案3，4。

#### 基于frame pointer的unwind stack技术与缺陷

源码：nuttx/arch/arm/src/common/arm_backtrace_fp.c

依赖 ARM 架构中的帧指针寄存器（FP，通常是 r7 或 r11，取决于指令集和编译配置）。

函数调用时，编译器会在栈上创建一个 “栈帧”（stack frame），FP 寄存器指向当前栈帧的固定位置（通常是栈帧底部），并在栈帧中保存上一层函数的 FP 值（形成 “FP 链”）和返回地址。

回溯时，通过 FP 寄存器找到当前栈帧，从中提取上一层 FP 和返回地址，再顺着 FP 链逐层向上追溯，直到栈顶。

如下图所示：

![](/img/openvela/image250.png)

在frame pointer的方案上，如果使用了thumb2，我们会遇到另一个GCC编译器的问题，这导致使用GCC编译器时无法使用这个方案：视频里讲解。

在GCC编译器生成代码中，fp(thumb2 r7)的保存值是压栈后的地址，由于压栈寄存器的个数不同，所以backtrace根本无法正确定位LR，而在clang编译器上的行为反倒不同，fp(r7)会直接加回栈顶指向LR，所以如果使用clang是可以正常完成栈回朔的，而arm的clang是需要license，在传统的低成本芯片中，没有人会花大价格来购买arm的toolchain，再加上fp的加入会导致应用程序的执行性能变慢，所以clang的方案也无法成型。

源码：nuttx/arch/arm/src/common/arm_backtrace_sp.c

### GDB体验

我们使用各种方法打印backtrace时，它的本质是使用如下机制之一在栈里找到“调用关系”，它们各有缺点：

- 基于arm eabi：对应openvela的“arm_backtrace_unwind.c”，占用Flash过大

- 基于frame pointer：对应openvela的“arm_backtrace_fp.c”，GCC编译器不支持

- 基于stack pointer：对应openvela的“arm_backtrace_sp.c”，不太精确

想得到精确的调用关系，可以使用人工分析——效率太低，最好的办法是使用gdb工具。

GDB是GNU开发的一个Unix/Linux下强大的程序调试工具。GDB主要帮你完成下面五个方面的功能：

- 启动你的程序，可以按照你的自定义的要求随心所欲的运行程序；

- 可让被调试的程序在你所指定的调置的断点处停住；

- 当程序被停住时，可以检查此时程序中所发生的事；

- 动态的改变你程序的执行环境；

- 离线分析功能。

GDB的使用流程主要有：（gcc）编译程序、启动gdb、运行程序、设置断点、单步执行、查看变量等，下面就从一个程序从编译到启动gdb进行调试到断点设置，单步执行到最后退出GDB调试整体流程进行介绍。

\# 此命令会将 core 文件大小限制设为无限制

\# 允许生成 core dump 文件

ulimit -c unlimited

\# 系统默认的 core dump 文件生成路径由

\# /proc/sys/kernel/core_pattern 控制

\# 若要让 core 文件生成在程序运行的当前目录

\# ./ 表示当前目录；

\# %e 代表程序文件名；

\# %p 代表程序进程 ID。

\# 这样设置后，core dump 文件会

\# 以 core.程序名.进程ID 的形式生成在当前目录。

echo "./core.%e.%p" \| sudo tee /proc/sys/kernel/core_pattern

当程序崩溃后会在当前目录下生成coredump文件，然后可以如此调试：

gdb ./test core.test.1234

我们使用各种方法打印backtrace时，它的本质是使用如下机制之一在栈里找到“调用关系”，它们各有缺点：

- 基于arm eabi：对应openvela的“arm_backtrace_unwind.c”，占用Flash过大

- 基于frame pointer：对应openvela的“arm_backtrace_fp.c”，GCC编译器不支持

- 基于stack pointer：对应openvela的“arm_backtrace_sp.c”，不太精确

想得到精确的调用关系，可以使用人工分析——效率太低，最好的办法是使用gdb工具。

在PC上我们可以直接使用GDB；但在跨平台、远程调试或嵌入式场景中，仅靠 GDB 无法满足需求 —— 此时GDBserver作为 “辅助者” 的角色便至关重要。二者并非独立工具，而是 “主从协作” 的关系，共同实现复杂环境下的程序调试。使用GDB+GDBServer 进行调试时，各个角色如下：

- GDB ：GDB 是调试流程的控制核心

- GDBserver：轻量级的调试代理程序，它接收GDB的命令来操作单板或程序

![](/img/openvela/image268.png)

比如人类输入“p g_a”命令想读取全局变量g_a的值时，GDB程序会解析被调试的程序得到g_a的地址addrA，然后向GDBServer发出“读内存addrA”的指令，GDBServer从单板或程序上读到addrA的数据，返回给GDB；GDB再显示给人类观看。

在实际调试过程中，“GDBServer”可以是一个软件：用来控制一个程序；也可以是“硬件+软件”，比如运行st-util模拟GDBServer，通过st-link去控制开发板。

人工分析、使用GDB分析的类比如下：

![](/img/openvela/image269.png)

方法1：人工分析时，需要根据反汇编文件的指令，去解析栈内容挑出LR。

方法2：GDB替代人工进行分析，也需要给它提供ELF文件（无需转成反汇编）、Coredump文件（来自Log，但是需要满足一定的格式）。在嵌入式开发里经常使用串口打印信息，openvela把这些信息使用压缩格式可视地打印出来，并且提供的coredump.py程序把这些信息转换为Coredump文件。比如执行“p g_a”命令时，GDB从ELF文件里解析出g_a变量的地址，然后去Coredump文件里读到这个地址的数值。

方法3：openvela提供了gdbserver.py程序，它可以模拟一个GDBServer。使用GDB程序去调试ELF文件时，各类读、写操作就是发给gdbserver.py的。我们需要把ELF文件、Log信息提供给gdbserver.py，它才知道寄存器值是多少、栈内容是什么。比如执行“p g_a”命令时，GDB从ELF文件里解析出g_a变量的地址addrA，然后向gdbserver.py发出“读内存addrA”的指令，gdbserver.py根据log信息返回数据给GDB。

#### Coredump的使用与内部机制

参考资料：  
nuttx/Documentation/guides/coredump.rst  
&lt;https://mi.feishu.cn/wiki/EjzZw2BHZiyYRbkYebgcEUoCnLe&gt;

程序崩溃时，异常处理函数会打印“Crash log”；还可以使用“dumpstack”命令查看任意任务的“backtrace”。

coredump功能与此类似：程序崩溃时异常处理函数会打印coredump信息（可以打印到串口，也可以存到Flash等），也可以使用“coredump”命令查看任意任务的coredump信息。

所谓coredump信息，是符合GDB程序格式要求的数据：里面的核心也是程序“快照”——程序崩溃瞬间的寄存器值、栈的内容，甚至可以含有其他内存的值。

使用coredump功能有2个好处：

- 把coredump信息提供给GDB：可以使用GDB分析崩溃的程序，得到精确的调用关系

- 使用coredump命令得到的信息，比dumstack命令所得的信息更全：dumpstack命令只会打印backtrace信息，不会打印栈内容。
