### RPMSG的概念与体验

#### 概念与作用

RPMSG（Remote Processor Messaging）的核心价值是让异构芯片里的多个处理器 “顺畅聊天、协同干活”，对初学者来说，不用纠结底层细节，先搞懂它能落地解决哪些实际问题。现代芯片（手机、工业控制器、车载设备）里不只有主 CPU（如 ARM/x86），还有专门的协处理器（DSP/MCU/ISP/NPU）—— 这些协处理器擅长做特定任务（比如音频处理、传感器计算、AI 推理），但没法直接和主 CPU 沟通，RPMSG 就是它们的 “对话工具”

#### 通信场景

openvela 支持各种各样的跨核通讯，从操作系统上来看，覆盖了从 Linux 到 openvela，openvela 到 openvela 的两种通讯模式，从底层的物理传输方式上来看，覆盖了基于 SPI/UART 等物理传输的通讯方式和基于共享内存&中断的通讯方式。

跨核通信可以分为：

① 片内异构核心间跨核通信

芯片内部存在多个异构核心，之间需要进行通讯，芯片间可以通过共享内存进行通信，这种场景下，芯片间一般会提供共享内存和中断机制。如下图所示：

![](/img/openvela/image162.png)

② 板级芯片间跨核通信

同一个 PCB 板中，多个芯片之间需要进行通讯，芯片之间通过物理通讯总线（比如UART、SPI）相连。如下图所示：

![](/img/openvela/image163.png)

③ 跨核间接通信

不存在直接物理连接通道的两个核心（Droid 和 Audio）需要进行跨核通讯，需要通过现有的跨核通道进行消息转发。如下图所示：

![](/img/openvela/image164.png)

④ 虚拟机之间跨核通信

在同一个 Hypervisor 上运行的多个虚拟机之间需要进行通讯，Hypervisor 会提供共享内存和中断机制。如下图所示：

![](/img/openvela/image165.png)

不同的跨核通讯场景，对应不同的底层物理通讯通道，在此之上的代码是没有差别的。

#### 体验

对于openvela，RPMSG有多种使用场景：

① Rpmsg Syslog：用于异构多核的跨核LOG输出，A核的打印信息通过B核的串口打印出来。

② Rpmsg Uart：用于异构多核的跨核 Uart 数据传输，在 AMP 系统中，有些业务需要使用虚拟串口设备和另外一个核心进行通讯。

③ Rpmsg Socket：用于异构多核的跨核 Socket 通讯，让不同核心的应用也可以通过 Socket 进行通讯。

④ Rpmsg Fs 用于异构多核的跨核文件系统访问，App 可以无感的访问远端 CPU 中的文件、目录，就像访问本核的文件系统一样。

⑤ Rpmsg Dev 用于异构多核的跨核字符设备访问，APP 可以无感的使用远端 CPU 中的字符设备，和使用本端的字符设备一样。

### RPMSG服务层注册情景分析

#### 核心链表

对于服务层、框架层、传输层，为了便于理解，我们先讲服务层，再讲传输层，最后讲框架层：从上、下两层开始阅读代码。

注意：RPMSG之间的通信，一般可以分为Client、Server两端。Client 端发送完成后，阻塞等待 Server 端的回复，Server 端收到消息后调用对应的系统 API 执行相关操作，拿到结果后回复消息，Client 端收到回复后，将获取到的结果再返回给用户。

阅读代码时，每个核的框架层“nuttx\drivers\rpmsg\rpmsg.c”有2个链表（Client、Server各有2个链表），它们是关键：

```
static METAL_DECLARE_LIST(g_rpmsg_cb);

static METAL_DECLARE_LIST(g_rpmsg);

```
g_rpmsg里存放的是“rpmsg”，对应“传输能力”，每个物理传输通道都对应一个“rpmsg”。比如示例中A板和B板使用UART进行通信，那么两个板子的g_rpmsg里都会有一个“uart rpmsg”。g_rpmsg里的链表项由底下的“传输层”提供。

g_rpmsg_cb里存放的是“服务层”提供的“rpmsg_cb”：对于Client里面存放的是当物理连接被创建、断开时的回调函数；对于Server里面存放的是Client发来创建endpoint的请求以便获得服务时的回调函数。

② server端收到服务请求后，调用rpmsgdev_ns_match确认能否提供支持

③ 如果能提供支持，server端调用rpmsgdev_ns_bind处理client端的“rpmsg_create_ept”请求，建立通信channel。

### RPMSG传输层注册情景分析

#### 函数执行过程分析

我们把A板、B板的串口连接后，数据通道的物理连接就建立了。但是，A板、B板不知道啊，它们还需要打招呼，确认对方的存在。这个过程分为6步：

① 假设A板的传输层先初始化：它通过串口发送连接请求（即发送一个字符“RPMSG_PORT_UART_CONNREQ”，0x7d）

② 但是B板的传输层尚未注册，所以A板无法获得回应，连接未建立

③ 当B板的传输层初始化时：它通过串口发送连接请求（即发送一个字符“RPMSG_PORT_UART_CONNREQ”，0x7d）

④ A板回应“RPMSG_PORT_UART_CONNACK”即0x7c，连接就建立起来了

⑤ client端（A板）调用之前服务层注册的cb-\&gt;device_created

⑥ 打招呼成功后，A板、B板各自的g_rpmsg链表里才有各自的rpmsg device

client端(A板）“vendor/allwinnertech/chips/r528/r528_boot.c”调用了如下代码：

struct rpmsg_port_config_s a_cfg = {"100ask_b", 4, 4, 200, 300};

rpmsg_port_uart_initialize(&a_cfg, "/dev/uart2", "100ask_a");

#### UART数据传输格式

整个 Rpmsg 消息从原始数据到实际传输出去的流程见上图，从原始数据开始，每一层都会根据自己本层的需求，填充一个数据头，类似网络协议栈栈的数据包的组成。如下图所示：

![](/img/openvela/image192.png)

在基于UART的传输层，它除了发送数据包之外，还可以发送一些命令，如下所示：

\#define RPMSG_PORT_UART_START 0x7f // 帧起始标记

\#define RPMSG_PORT_UART_END 0x7e // 帧结束标记

\#define RPMSG_PORT_UART_CONNREQ 0x7d // 连接请求

\#define RPMSG_PORT_UART_CONNACK 0x7c // 连接确认

\#define RPMSG_PORT_UART_ESCAPE 0x7b // 转义字符

\#define RPMSG_PORT_UART_ESCAPE_MASK 0x20 // 转义掩码

比如建立物理通道时，一端发送字符RPMSG_PORT_UART_CONNREQ（0x7d），另一端回复RPMSG_PORT_UART_CONNACK（0x7c）。

当发送数据包时，流程如下：

① 发送 RPMSG_PORT_UART_START(0x7f) 标记帧开始

② 对数据进行转义处理：

\- 如果数据字节在 RPMSG_PORT_UART_ESCAPE（0x7b）和RPMSG_PORT_UART_START（0x7f）范围内（特殊字符）

\- 先发送 RPMSG_PORT_UART_ESCAPE (0x7b)

\- 再发送 (原字节 XOR 0x20)

\- 例如：0x7f → 0x7b 0x5f

③ 发送RPMSG_PORT_UART_END(0x7e) 标记帧结束

在传输层，没有endpoint的概念，它只负责把数据包完整地发个对方，并且让对方能识别出来。
